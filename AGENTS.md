# ERP engineering rules

- Deliver incrementally by dependency-aware modules/capability slices from the accepted backlog.
- Solve actual factory users' workflow needs; operational clarity outranks technical sophistication.
- Avoid speculative features, clever abstractions and unnecessary infrastructure or dependencies.
- Follow accepted architecture, recorded factory evidence and live OQ statuses; invent no business rules.
- Read only the current task's relevant canonical sources; use targeted search and the document index.
- For meaningful capabilities follow [DEVELOPMENT_WORKFLOW.md](docs/12-implementation-planning/DEVELOPMENT_WORKFLOW.md).
- Lifecycle: design/plan -> implement -> test -> review -> fix -> acceptance -> document -> commit.
- Define a bounded business goal, users, invariants, dependencies, exclusions and Definition of Done.
- For substantial work use a concise task execution plan; do not grow permanent context files.
- Implement core workflow first, required operational features next, optional enhancements later.
- Preserve the Modular Monolith, module write ownership and published dependency directions.
- PostgreSQL is canonical transactional state; preserve atomic bundles through owner ports.
- ACT-IPS alone posts inventory; Ledger is truth, Balance rebuildable, kg authoritative, no negative stock.
- Preserve production/genealogy/sales invariants; MVP excludes QC and portal ordering.
- Use frozen exact versions and root scripts; review necessary changes rather than silently upgrading.
- Development/validation is Windows-only; do not use Ubuntu/WSL/Linux or add Linux CI jobs.
- Exercise database/concurrency/crash invariants against real PostgreSQL with isolated test roles/databases.
- Test relevant behavior and failure modes; never mock away the behavior being verified.
- Keep credentials, customer data and unsafe payloads out of source, logs and review artifacts.
- Security and independent engineering review are part of every meaningful slice's Definition of Done.
- Close blocking defects and required improvements; never accept with failed relevant tests or known high/critical defects.
- Use relevant project skills in .agents/skills and suitable specialist subagents when they improve quality.
- Review third-party skill source/execution/dependencies/network/data handling before any installation.
- Update canonical implementation documentation to describe delivered behavior, limits and deferred work.
- Before committing review the final diff and relevant checks, including git diff --check.
- After acceptance create a coherent local commit; report hash, tests, reviews and ready-to-push status.
- Never push remotely or rewrite history without explicit authorization.
- Obey effective Owner authorization, canonical gate/unlock and [current scope](docs/00-governance/CURRENT_PHASE.md).
- Never self-authorize implementation or fabricate human approval; tool access is not approval.
- Native/OS containment is retired; do not revive installers, ACL hardening or micro-permission hooks.
