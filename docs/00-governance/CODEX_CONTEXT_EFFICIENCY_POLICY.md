# Permanent Codex context efficiency policy

Effective 2026-11-08 under the actual Owner's **Permanent Owner Directive —
Project-Wide Codex Context and Token Efficiency Policy**. This repository-backed
operating policy applies to every ERP task, phase, maintenance activity, future
session and delegated agent until the Owner explicitly amends or revokes it.
Its objective is maximum engineering quality per token. Do not reduce reasoning
capability, verification or engineering judgment to save tokens.

Security, correctness, accepted contracts and governance requirements take
precedence. This policy grants no implementation authority or additional write
permissions. Follow current [Owner scope](CURRENT_PHASE.md), effective gate/unlock
and the [development workflow](../12-implementation-planning/DEVELOPMENT_WORKFLOW.md).
Never modify protected instructions, gates, hooks, security controls or persistent
permissions without the required separate authorization; prepare a proposed diff
and request Owner approval if a required instruction update is blocked.

## Default task sequence

1. Identify the exact authorized scope and authoritative sources.
2. Locate the minimum necessary context using the [document index](../INDEX.md),
   targeted searches and relevant sections; read complete contracts when needed.
3. Reuse reliable active-session context, verified paths, sections, revisions and
   concise findings. Revalidate when the revision, contract or evidence changes.
4. Retrieve further evidence as needed; do not automatically reload architecture,
   roadmaps, governance history or prior phases, or reread unchanged sources.
5. Execute with full engineering rigor and effort proportionate to the risk.
6. Retain complete required verification evidence, with concise model-facing
   results. Preserve all diagnostics needed to investigate failures.
7. Report concise conclusions with traceable sources and actual check results.
8. When continuation is needed, preserve a compact handoff as described below.

## Retrieval, output and handoffs

Use focused commands, bounded output and relevant diffs. Avoid broad directory
listings and full-file dumps when targeted reads answer the question. Keep complete
test logs in the appropriate evidence location; expand diagnostics when needed.
Never suppress errors, hide failures, discard necessary evidence or substitute
unsupported summaries.

A continuation handoff records the current task and authorized scope, relevant
baseline commits, authoritative document references, completed work, outstanding
decisions, known risks and required next actions. Reuse it instead of reconstructing
project history, but newer repository evidence outranks an old summary. Keep
handoffs task-specific; do not grow permanent project-history context files.

## Delegation and independent review

Give each reviewer a precise scope, relevant entry points and authoritative
references. Supply the baseline and proposed diff as appropriate, without copying
the entire history or duplicating investigations unnecessarily. Request concise,
evidence-backed findings. Independent verification may intentionally repeat work.
Reviewers must inspect sources and retain freedom to expand their investigation;
implementer conclusions alone are insufficient review context.

Preserve all required engineering, security, database and QA reviews and reviewer
independence. Efficiency never waives a required review or closes its findings.

## Existing capabilities and skills

Evaluate installed capabilities first. Prefer targeted navigation and progressive
disclosure; for substantial dependency/impact analysis use the existing local
[Graphify skill](../../.agents/skills/graphify/SKILL.md) and verify against sources.
Do not assume a skill provides automatic caching or token savings.

Do not create or install a skill merely because it might help. A demonstrably
beneficial new skill or retrieval mechanism needs a proposal covering purpose,
expected improvement, context-loading behavior, security, maintenance and existing
alternatives. Obtain separate Owner authorization before installing dependencies,
third-party skills or changing pinned skill configurations. Follow existing
provenance, execution, network and data-handling review requirements.

## Proportionate verification and non-negotiable quality

Small, low-risk changes use focused investigation and verification. Architectural,
security-sensitive, database, transaction-critical and acceptance work retains the
complete required analysis and verification. Do not repeat unchanged expensive
suites without a technical or governance reason; always run complete regression
and acceptance verification when the applicable gate mandates it.

Never weaken authorization/customer isolation, transaction consistency, idempotency,
durable command recovery, audit integrity, migration governance, independent
reviews, real PostgreSQL/Chromium verification, evidence retention or Owner gates.
Preserve accurate conclusions and all security requirements.
**Eliminate redundant work, never required work.**

## Measurement and improvement

When native usage information is available, periodically assess repeated reads,
excessive output/searches, duplicated agent context, repeated instruction loading
and avoidable session reconstruction. Use actual token metrics when available;
otherwise label qualitative findings or proxies. Never invent savings percentages
or performance measurements. Correct clear inefficiencies without creating a
recurring high-cost monitoring process. No automated monitoring, background services
or external telemetry without authorization. Report efficiency issues only when
they materially affect execution or require an Owner decision.

## Initial adoption and limits

The Owner explicitly authorized this documentation-only adoption and local commit
from clean baseline `ac1395e2da36ef84b9c2e3a9c43bc91a1690281a`. The root
`AGENTS.md` links here and the document index provides discovery. The canonical
`.cursor/architecture-gate.json` permits `AGENTS.md` and `docs/**/*.md`; neither
is a protected control path. No gate, unlock or permission change is needed.

Review of current instructions, the development workflow and existing Graphify
policy found sufficient navigation capabilities. Qualitative efficiency risks are
long historical scope records, overlapping instruction sources and unbounded
output; the initial discovery batch itself returned excess text. Targeted sections,
source precedence and bounded subsequent reads address these without changing
historical records. No precise token savings were measured or claimed; no new skill,
dependency, retrieval service or monitoring mechanism is proposed.

Adoption changes only this policy, one root instruction and its index entry.
Source/link/diff and independent governance/security consistency review are relevant;
unrelated product tests are not required by the workflow for documentation changes.
This records no ERP capability delivery or acceptance, changes no current phase,
and authorizes no P4c/P4d/P5 implementation, push or deployment. Existing product,
architecture, business, migration, index and security policies remain authoritative.
