**OQ-017 — Inventory Posting Mechanism**

**Decision:** Inventory posting is application-owned and executed within explicit PostgreSQL transactions, protected by database row locks, constraints, and transactional invariants.

### Authoritative posting boundary

Inventory business commands are orchestrated by the application/domain layer.

The application owns the business workflow for operations such as:

- Goods Receipt
- Issue
- Reservation
- Allocation
- Consumption
- Production Output
- Residual creation
- Scrap posting
- Shipment-related inventory posting

The Inventory Ledger remains the authoritative inventory fact store.

### Transaction boundary

A posting command must execute all required state changes and Ledger facts within an explicit PostgreSQL transaction.

For concurrency-sensitive operations, the implementation must use appropriate PostgreSQL locking and/or constraint mechanisms to prevent lost updates, double reservation, negative available stock, and other invariant violations.

Conceptually:

**BEGIN → lock relevant rows → validate invariants → write authoritative facts → update required transactional state → COMMIT**

### Database enforcement

PostgreSQL remains responsible for enforcing structural and concurrency-related guarantees that are appropriately expressed through:

- foreign keys,
- unique constraints,
- check constraints,
- transactional isolation,
- row-level locks,
- appropriate indexes.

The application must not rely solely on pre-checks performed outside the transaction.

### Stored functions

PostgreSQL stored procedures/functions are **not** the default authoritative posting mechanism.

A future PostgreSQL function may be introduced for a specific performance or concurrency requirement only after an explicit technical spike and architecture decision.

No current design decision should assume PostgreSQL functions as a required dependency.

### Ledger and projections

Balance and Genealogy remain derived/rebuildable projections of authoritative Ledger facts.

A posting command must not directly treat Balance or Genealogy as an independent source of truth.

### Idempotency

All externally retryable posting commands must define idempotency behavior appropriate to the command.

A repeated submission must not create duplicate authoritative Ledger facts.

### Architectural principle

> Business transaction orchestration belongs to the application/domain layer; PostgreSQL provides transactional atomicity, locking, and structural enforcement. Database functions are an optimization/design option, not the default business-command boundary.

**Status:** Accepted as the recommended posting baseline. Any use of PostgreSQL functions for authoritative posting requires a separate ADR supported by a technical spike.
