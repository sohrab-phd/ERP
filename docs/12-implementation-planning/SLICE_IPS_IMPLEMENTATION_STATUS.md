## Implemented responsibility / public ports

`apps/backend/src/modules/inventory/` contains public contracts, exact Kg and
InventoryPostingService. `post(context,effects)` is the sole internal quantity
writer: context carries current actor, admitted outer command and opaque active
transaction. Effects are bounded, validated and snapshotted before awaiting:

| Effect | Implemented responsibility |
| --- | --- |
| STOCK_IN | Positive exact kg; new valid Unit AVAILABLE, existing AVAILABLE metadata must match |
| STOCK_OUT | Positive physical decrease; unreserved issued/partial Unit under CompleteProductionOperation or PACKED under DispatchShipment; terminal state matches remaining kg |
| RESERVE | Positive claim under ActivateReservation, explicit confirmed-demand priority policy, one ACTIVE claim even if partial; available cannot be negative |
| RELEASE | Terminal RELEASED/CONSUMED removes reserved only; consume requires owning issue/shipment boundary and eligible destiny |

`snapshot` returns validated Ledger totals after claim/projection reconciliation.
`rebuild` requires explicit maintenance/resource permission and restores Balance
from valid Ledger/claims; no new movement, outcome or audit is generated by this
internal port. The future authorized maintenance command owns its own audit.
No arbitrary Unit metadata/move API or independently editable Balance is exposed.
`PostingPolicy` supplies current authorization, locked domain/target eligibility,
reservation priority and maintenance access. Composition injects deny-default
policy, an empty business registry and no inventory HTTP route. ACT-IPS is the
executor, never an individual account/role grant.

The SQL adapter lives solely at
`apps/backend/src/infrastructure/postgresql/inventory-store.ts`. All operations
use the same transactionClient capability and installation/authority predicates;
no pool, nested commit, own retry or foreign module table write. Production
adapter import is confined to composition; the module uses its public port.
The ownership checker rejects transport imports and literal inventory SQL bypasses.

## Persistence / transaction contract

Migration `database/migrations/0005_inventory_posting.sql` creates only:

- `inventory.unit`: scoped UUID identity, opaque lot/location IDs, kind/customer
  scope and accepted lifecycle; no independent quantity column or QC field.
- `inventory.ledger`: immutable scoped signed kg deltas and source fact/effect
  identities, optional same-Unit original reference, canonical material binding,
  ACT-IPS plus actual caller/request/command/version/key provenance and DB time.
- `inventory.balance`: checked on-hand/reserved projection; available is derived.
- `inventory.reservation`: positive claim and ACTIVE/RELEASED/CONSUMED terminal
  bookkeeping; scoped partial uniqueness enforces one ACTIVE claim per Unit.

Exact BigInt arithmetic and nonrounding NUMERIC checks use the technical capacity
in [ADR-0015](../00-governance/adrs/ADR-0015-inventory-posting-kernel.md). This does
not approve fractional measured weights: accepted factory tickets remain whole kg.
No conversion factor, threshold or descriptive count stock total is invented.

Scoped Unit/effect/reservation advisory keys lock in actual bigint order, then
existing Units lock FOR UPDATE in UUID order. Fresh Ledger/claim/projection reads
and all mutations occur on the same caller-owned transaction. Source effect is
unique across Units within authority; same intent under new key returns DUP,
changed binding CONFLICT, and production completion new-key duplicate always
CONFLICT. Identical command-key retries replay accepted or rejected envelope
outcome. Rejection rolls back handler effects; technical failures abort the whole
transaction. AUD-CMD-ACCEPTED/REJECTED/REPLAYED retain their established meaning.

Runtime test grants are schema USAGE, Unit/Balance/Reservation SELECT/INSERT/UPDATE
and Ledger SELECT/INSERT. Migration owner is a separate non-superuser. Direct
Balance editing is not an application capability; its DML grants support only
the owned projection adapter. Trusted code ownership checks and real privilege
tests are engineering controls, not an adversarial OS containment claim.
