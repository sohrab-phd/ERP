## Delivered responsibility and workflow

Finance-Lite records immutable evidence of an already-issued customer invoice.
This preserves the factory's Sales invoice workflow and independent external
accounting registration. No invoice is generated by this software. The evidence
UUID identifies each record; reference/date/order/customer describe it. Different
genuine records may share a reference or order; no official numbering, fiscal
sequence or one-invoice-per-order policy is inferred.

Only an individually authenticated current organizational ACT-SALES can record
and read evidence. Current organizational ACT-FIN reads only. ACT-SEC manages
grants through existing Identity but receives no automatic invoice access.
Customer-scoped grants and Procurement/Production/Warehouse/Shipping/portal/other
roles are denied. Role titles and employee names confer no software permission.
Trusted installation/authority and personally issued session contexts are used;
copied contexts and client identity/organization overrides cannot supply authority.

The Sales-owned `invoiceReference` port validates existing order/customer in the
same transaction through existing scoped SalesStore contracts and the Sales FK.
It returns only canonical order/customer IDs, never commercial internals. No
confirmed/delivered order state was required by the Owner, so the evidence port
does not introduce that gate. Existing customer-scoped Sales workflows remain
unchanged. Finance-Lite never imports Sales persistence or writes Sales state.

## Public contracts

POST `/finance/invoice-evidence`: `RecordIssuedInvoiceEvidence`, contract v1,
target kind `invoice-evidence` with a stable UUID, stable UUID idempotency key,
empty preconditions and exactly four payload fields:

| Field                    | Contract                                                                                                                              |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| invoiceDocumentReference | Nonempty valid Unicode, no controls, <=128 UTF-8 bytes; meaningful external reference supplied by authorized Sales user               |
| issueDate                | Real YYYY-MM-DD calendar date in years 0001-9999; actual issue date supplied by user, no invented shipment or future-date restriction |
| salesOrderId             | Existing canonical Sales order UUID in the trusted organization                                                                       |
| customerId               | Existing owning customer UUID matching that order in the same organization                                                            |

Actor, organization, time, money, status and extra fields are rejected. Successful
command data is `{ evidenceId }`, event `IssuedInvoiceEvidenceRecorded`. No invoice
state or monetary balance is returned. Missing/mismatched/foreign Sales references
share a safe GUARD_STATE rejection. New keys on occupied UUIDs reject
GUARD_IDEMPOTENT_DUP for equal facts or GUARD_CONFLICT for changed facts.

GET `/finance/invoice-evidence/{uuid}`: `GetIssuedInvoiceEvidence`, returning id,
the four documentary fields, trusted authentication principal issuer/subject and
database recordedAt. Issuer/subject attribute the actual authenticated recorder;
no separate external preparer identity is invented. Binding, credentials, session
data and finance state are omitted. Missing/foreign organization facts yield 404.

Existing personal bearer sessions, closed/bounded JSON body, no-store safe
responses, route/method checks, duplicate-selector checks, Origin rejection,
16-active-operation bound, transaction/SQL deadlines apply. Writes also use the default command-admission recovery fence.
`x-erp-role` selects an explicitly granted role (ACT-SALES default; ACT-FIN reads
only), never grants it. Customer-scope selection headers are rejected. Outcomes
use existing 200 accepted/replay, 422 durable rejection, 409 bound-key conflict,
401/403 personal/current-access denial, 400 invalid, 404 absent, 405 method and
503 technical/uncertain response conventions. Technical uncertainty is resolved
with the original key, not a fresh-key duplicate.

## Persistence, integrity and ownership

Additive migration `0016_invoice_evidence.sql` creates `finance.invoice_evidence`.
Scoped PK is installation/authority/evidence UUID. Scoped composite FK references
the existing Sales order/customer unique key; Sales already requires the customer
to exist in that organization. Store documentary facts/binding, principal issuer/
subject, ACT-SALES, request/key and DB clock timestamp. Date/reference/role bounds
and FK are enforced in PostgreSQL. No reference-uniqueness index or Sales mutation.

Runtime receives finance USAGE and SELECT/INSERT only; UPDATE/DELETE/TRUNCATE/DDL
are denied. Owner and runtime remain distinct restricted roles. Application
advisory identity lock serializes competing evidence UUIDs, followed by fresh
lookup and current authorization. Permission is rechecked after Sales validation;
reads recheck after their lookup. Fact, terminal outcome and decision audit share
one envelope transaction, including rollback on late handler/audit/outcome failure.
Accepted/rejected replay rechecks current authorization before disclosure.

Audit retains the original organizational actor grant and trusted personal
attribution. The scoped fact UUID links the mandatory owning customer/order on
the immutable evidence record; no documentary customer payload is copied into
audit/log safe details. See [audit semantics](../06-security-rbac-audit/AUDIT_TAXONOMY.md).
